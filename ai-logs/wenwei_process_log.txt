2) Second Prompt (Issue 1 Fix — track order in GET /{id}):

    My GET /api/playlists/{id} returns the playlist and its tracks correctly, but
    the tracks come back in a different order on every refresh. The frontend
    (Matthew's PlaylistDetailPage) renders them in whatever order I send. My
    repository call is:

        List<PlaylistTrack> tracks = playlistTrackRepository.findByPlaylistId(id);

    The trackOrder column is populated correctly in MySQL (1..N). Why are they
    coming back unordered?

Second Output Response (Issue 1 Fix):
    JPA does not guarantee any ordering on a derived query unless you ask for one.
    Without an ORDER BY clause, MySQL is free to return rows in whatever physical
    order is cheapest — which after a few inserts and updates is no longer the
    insertion order. Use an explicit @Query with ORDER BY t.trackOrder ASC so the
    contract is visible at the repository level (and you can still keep the short
    method name findByPlaylistId at the call sites).

Second Changes (Issue 1):
    In PlaylistTrackRepository.java, replaced the bare derived query with an
    explicit JPQL @Query:

    Before:
        List<PlaylistTrack> findByPlaylistId(int playlistId);

    After:
        @Query("SELECT t FROM PlaylistTrack t WHERE t.playlist.playlistId = :playlistId "
             + "ORDER BY t.trackOrder ASC")
        List<PlaylistTrack> findByPlaylistId(@Param("playlistId") int playlistId);

    Tracks now consistently come back in trackOrder 1..N. The same @Query
    pattern was applied to PlaylistRepository for the user-id lookup so both
    repositories use explicit JPQL instead of derived names.

3) Third Prompt (Issue 2 Fix — LazyInitializationException on save):

    POST /api/playlists/save persists everything correctly to the DB, but the
    response throws a LazyInitializationException when Jackson tries to serialize
    the saved Playlist. Stack trace points at Playlist.user. I am returning the
    saved entity directly:

        Playlist saved = playlistRepository.save(playlist);
        return ResponseEntity.ok(saved);

    User is @ManyToOne(fetch = LAZY). What's the right fix — switch to EAGER, or
    something else?

Third Output Response (Issue 2 Fix):
    Don't switch User to EAGER — that will cascade the same problem onto every
    other entity that references User and balloon query times. The right fix is to
    stop returning JPA entities from the controller layer at all. Instead build a
    response Map with only the fields the frontend actually needs (playlistId,
    title, createdAt, mood, tracks[]). A small private buildPlaylistResponse()
    helper keeps the shape consistent across save / get / share.

Third Changes (Issue 2):
    Added a private helper in PlaylistController:

        private Map<String, Object> buildPlaylistResponse(Playlist playlist,
                                                          List<PlaylistTrack> tracks) {
            Map<String, Object> response = new LinkedHashMap<>();
            response.put("playlistId", playlist.getPlaylistId());
            response.put("title",      playlist.getTitle());
            response.put("createdAt",  playlist.getCreatedAt());
            if (playlist.getMood() != null) { ... moodMap ... }
            List<Map<String, Object>> trackList = new ArrayList<>();
            for (PlaylistTrack t : tracks) { /* trackId, trackName, ... */ }
            response.put("tracks", trackList);
            return response;
        }

    Before:
        Playlist saved = playlistRepository.save(playlist);
        return ResponseEntity.ok(saved);

    After:
        Playlist saved = playlistRepository.save(playlist);
        playlistTrackRepository.saveAll(tracks);
        return ResponseEntity.status(HttpStatus.CREATED)
                             .body(buildPlaylistResponse(saved, tracks));

    No more LazyInitializationException, the User entity (with passwordHash) is
    no longer leaked on responses, and getPlaylist() / sharePlaylist() reuse the
    same helper for a consistent shape.

    GET /api/playlists/shared returns 500 with NumberFormatException: For input

        @GetMapping("/{id}")    public ... getPlaylist(@PathVariable int id, ...)
        @GetMapping("/shared")  public ... getSharedWithMe(...)

    declared in that order. Spring MVC is matching the literal path "shared"

Sixth Output Response (Issue 5 Fix):
    The cleanest fix is to declare the more specific (literal) route BEFORE the
    variable {id} route. Spring MVC's RequestMappingHandlerMapping prefers the
    most specific match, but when two routes are at the same specificity level
    declaration order matters for how the registry walks them. Move @GetMapping
    ("/shared") above @GetMapping("/{id}") in the source file. Don't rename the
    endpoint — Matthew's SharedWithMePage is already calling /api/playlists/shared.
