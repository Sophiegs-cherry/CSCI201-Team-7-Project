SESSION 2: Registration flow implementation & DB safety
================================================================================


PROMPT 2: What should the `register` endpoint do (validation, hashing, persistence, response)?

AI RESPONSE SUMMARY:
- Validate `RegisterRequest` (non-empty username/email, password length) using bean validation annotations (DTOs present in `backend/src/main/java/com/moodtunes/dto/`).
- Use `UserRepository.existsByUsername()` / `existsByEmail()` to provide quick feedback for duplicates and rely on the database unique constraints (defined in `User` entity) as a final guard.
- Wrap the actual save in a `@Transactional` `AuthService.register()` method and hash passwords with `PasswordEncoder` (BCrypt) before persisting.


WHAT I LEARNED:
- DTOs are in `backend/src/main/java/com/moodtunes/dto/` and entities in `backend/src/main/java/com/moodtunes/model/` — keep mapping consistent.

ISSUES ENCOUNTERED:
- Race conditions where two simultaneous register requests can both pass `existsBy...` checks and trigger a DB unique constraint violation.

HOW I FIXED IT:
- Keep `existsBy...` checks for friendly errors and also catch `DataIntegrityViolationException` to return `400 Bad Request` with `MessageResponse` when the DB rejects duplicates. Ensure `AuthService.register()` is `@Transactional`.

SESSION 3: Login flow, token issuance, and response payloads
================================================================================


PROMPT 3: How should login authenticate users and issue tokens consumable by the frontend?

AI RESPONSE SUMMARY:
- Accept `LoginRequest` and use `UserRepository.findByUsername()` (or email) to retrieve the user.
- Use `PasswordEncoder.matches()` to verify the submitted password.
- On success, generate a JWT token via `JwtTokenProvider` and return `AuthResponse` containing the token and minimal user info. The application uses stateless JWT auth (no server session is created).


WHAT I LEARNED:
- `AuthResponse.java` already exists in `backend/src/main/java/com/moodtunes/dto/` — reuse it rather than crafting ad-hoc JSON.
- The frontend should accept the JWT and send it in `Authorization: Bearer <token>` headers for subsequent requests rather than relying on cookies.

ISSUES ENCOUNTERED:
- Bad credentials must yield `401 Unauthorized` with a `MessageResponse` body rather than `500`.

HOW I FIXED IT:
- `AuthController.login()` returns `ResponseEntity.status(HttpStatus.UNAUTHORIZED)` when `PasswordEncoder.matches()` fails and logs `LOGIN_FAILED` events. On success it returns `AuthResponse` with a JWT created by `JwtTokenProvider`.

SESSION 7: CORS, CSRF, and frontend integration details
================================================================================


PROMPT 7: How to integrate frontend for token-based auth and what CORS/CSRF details matter?

AI RESPONSE SUMMARY:
- `CorsConfig` is present (`backend/src/main/java/com/moodtunes/config/CorsConfig.java`) and should allow the frontend origin. For JWT auth, CORS must allow the frontend to send `Authorization` headers.
- CSRF concerns are different for JWTs; if cookies are not used, CSRF risk is reduced, but secure token storage on the client (e.g., memory/localStorage tradeoffs) should be considered.

WHAT I LEARNED:
- The frontend should send the JWT in `Authorization` headers on each request. `withCredentials` is not required for tokens unless cookies are used.

HOW I FIXED IT:
- Verified `CorsConfig` allows the frontend origin; documented that the frontend must include the `Authorization: Bearer <token>` header after login.
